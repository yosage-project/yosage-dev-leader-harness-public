# よくある詰まり

## リーダーが起票したところで止まった

想定どおりです。`/yosage-dev-leader-harness:leader-loop` は**起票までで止まり**（束ねる場合は起票の手前）、実装の着火はしません。
リーダーは、次に人が引くトリガをコマンドの形で示します。単発の issue なら
`/yosage-dev-harness:issue-implement <owner>/<repo>#<N>` です。束ねた一括起票（Epic）は段階0の外なので、起票の手前で
止まり、計画を示して `/yosage-dev-harness:epic-create-docs <epic-name> <概要>`（計画を書く）と
`/yosage-dev-harness:epic-create-issues <epic-title>`（一括起票）を案内します。起票したあとは
`/yosage-dev-harness:epic-implement <owner>/<repo>#<N>` で実装に入ります。
それを実行すると、本体の実装の流れに入ります。理由は [authority.md](authority.md) の段階0と、本体の
`implement-routing`（着火が重い遷移は人がトリガ）です。

## リーダーが「止まります」と報告してきた

[authority.md](authority.md) の「止まる条件」のどれかに当たっています。報告には「どこまで進んだか」と
「何が判断を要するか」が書かれているはずです。その判断に答えると続きます。

- 段階の表に無い操作が要る、または対象範囲が外に及ぶ: 許可するなら、その操作を人が指示します。
- 規律、既存の知見、受け入れゲートの設定に触る: 変更の中身を見て、承認するかを決めます。
- 受け入れ条件が書けない: 要望を具体化する情報（誰が、何で、どの状態を見て満たしたと言うか）を渡します。

止まる回数が多くて定常の接点のようになっているなら、工程の区切りの入れ直しが必要です。

## 要件の確認が何度も差し戻される

要件化ゲートで毎回大きく差し戻されるなら、通しで進める設計が早すぎます。リーダーが何をどう読んでその要件に
したか（解釈の理由）が、実際の意図と食い違っている可能性があります。ゲートの説明のうち、理由の部分に反論して
ください。

## 入口が入らない（リーダーとして振る舞わない）

- プラグイン `yosage-dev-leader-harness` と、本体 `yosage-dev-harness` の**両方**が、同じ案件で有効になって
  いるかを確認します。本体が無いと、規律が参照する本体のスキル・エージェント・ルールが無く、規律が成立
  しません。
- 導入のコマンドを実行したディレクトリ（ワークスペースならそのルート、単一リポジトリならそのリポジトリ）で
  `claude` を起動しているかを確認します。`README.md` の「導入」は、その場所で導入すると、有効化の設定が
  `.claude/settings.json` に書かれる、と述べています。別の場所で起動すると、その設定が読まれないことがあります
  （起動場所と入口の関係を、Claude Code の仕様として確かめたものではありません）。
- 入口が入るのは**メインのセッションだけ**です。サブエージェントには入りません。サブエージェントの中で
  リーダーとして振る舞わないのは、正しい動作です。
- 規律スキル（`authority` など）は `/` のメニューに出ません。入口の案内に従って、リーダーが判断の前に読み込みます。
  人が打つコマンドは `/yosage-dev-leader-harness:leader-loop` です。

## セッション開始時にフックのエラーが出る

「リーダーの入口が読めないため、注入できませんでした」という趣旨のメッセージが出たら、プラグインのファイルが
欠けています。プラグインを入れ直してください。

## 入口が二重に入る

次のどちらかです。

- 同じ名前のプラグインを、開発用とリリース用の2つのマーケットプレイスから同時に有効にしている。どちらか
  一方にします。
- 旧ハーネス本体の、リーダーの入口を注入するフックが残っている。リーダー側の旧ファイルを消しても、このフックは
  消えません。`README.md` の「旧版（CLI で入れた導入先）からの移行」の手順1（ハーネス本体を新しいプラグインへ
  移す）と手順2（旧ハーネス本体の入口のフックが無くなったことを確かめる）を見直します。順序を入れ替えない
  でください。

## マーケットプレイスの取得で認証に失敗する

リリース用のリポジトリが非公開の間は、手元に GitHub の git の資格情報が保存されている必要があります
（`gh auth login` のあとに `gh auth setup-git` など）。Claude Code は、マーケットプレイスの取得や更新の確認で
入力を求めず、保存済みの資格情報だけを使います。

## 更新が届かない

更新は、プラグインの `version` が上がったときだけ届きます。自動更新は既定で無効なので、`/plugin` の
Marketplaces で有効にするか、`/plugin marketplace update` を実行します。

## マージ推奨が古いと言われた

マージ推奨は、特定の状態（コミット）に対する表明です。修正が入って状態が変わったら、リーダーは既存の
コメントを編集せず、**新しいコメントとして出し直す**決まりです。推奨に書かれたコミットが、PR の現在の
状態と合っているかを確認してください。内容の変化を説明するコメントだけでは、出し直しになりません。

## リーダーが実装しない

仕様です。リーダーはメインのセッションとして、要件化・裁定・投入指示を行い、実装は実装役（本体の
`yosage-dev-harness:implementer`）に投入します。

## 案件固有の取り決めを足したい

導入先に規律のコピーは置かれないので、案件固有の適応は案件のリポジトリのルール（`.claude/rules/` 等）に
書きます。一般化できそうな変更は、リーダーが報告を提案します。配布元へ起票するのは、人が明示して指示した
ときだけです。
