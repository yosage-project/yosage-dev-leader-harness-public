# はじめての1件

## 始める前に確かめること

- 本体 `yosage-dev-harness` と、この拡張 `yosage-dev-leader-harness` の**両方**が、同じ案件で有効になっている
  こと（導入は `README.md` の「導入」）。
- 導入のコマンドを実行したディレクトリ（ワークスペースならそのルート、単一リポジトリならそのリポジトリ）で
  `claude` を起動すること。導入するとそこの `.claude/settings.json` に有効化の設定が書かれます。
- 入口が入っているかは、新しいセッションの最初に「リーダーの入口」が1回だけ入っていることで見分けます
  （リーダーに「入口の案内に載っているスキルは？」と尋ねても確かめられます）。入っていないとき、二重に入るときは
  [troubleshooting.md](troubleshooting.md) を見てください。

## 本体だけのときとの違い

本体だけのときも、人が「この issue を実装して」と渡し、メインのセッションが実装役へ投入し、draft PR と一次
レビューを経て、人がマージします。本体にも、価値のトレードオフは前例があれば適用し無ければ人へ上げる手順
（`yosage-dev-harness:grounded-design`、PR のレビュー指摘への対応）や、衝突グラフで作業をウェーブにまとめる
手順（`yosage-dev-harness:orchestrate-parallel`）があります。

拡張が足すのは、それらを**案件の統制として常時担う役と、その型**です。本体の手順は、その作業が出たときに使う
道具です。拡張を足すと、メインのセッションが要件化から裁定・投入・マージ推奨までを一貫して受け持ち、裁定を
前例として残します。

| 場面 | 本体だけ | 拡張を足したとき |
|---|---|---|
| 要望を受け取る | 会話の流れで進む | 受け入れ条件つきの要件に直し、**そう解釈した理由**を説明して、納得を得る（要件化ゲート） |
| 判断が出る | 前例があれば適用し、無ければ人へ上げる | 上げる前に「調べれば決まるか」を先に分け（接地）、対象も blocking な未決の問い・例外・watchdog の判断などに広げる。人が裁定したら、理由と反証条件を前例として残す |
| 複数の issue を流す | 衝突グラフでウェーブにまとめる | そのうえで、投入前の確認（共有資源の占有枠の明示、設計判断が要る issue は確定させてから投入）、順序の優先づけ、分けた理由を残すことを足す |
| 実装役へ渡す指示 | メインが書く | 毎回確認する項目（作業領域・起点と止める地点・検証の構成・スコープの縁など）に沿って書く |
| マージの前 | 人が PR を見て判断する | リーダーが、推奨か保留かを理由と検証内容つきで PR コメントに残す。マージ自体は人が行う |

導入すると、セッションの開始時に「リーダーの入口」が**メインのセッションにだけ**入ります。サブエージェントには
入りません。入口は、規律スキルの一覧と「判断の前に該当するスキルを読み込む」という取り決めを述べたものです。
規律の本文は、リーダーがその都度読み込みます。

## はじめての1件の流れ

「これをやりたい」を渡す入口は、`/yosage-dev-leader-harness:leader-loop` です。

```text
/yosage-dev-leader-harness:leader-loop 利用者がCSVで一覧を書き出せるようにしたい
```

引数は自由な文です。「やりたいこと」でも「ここが課題」でも構いません。

### 1. リーダーが受け取り、起票まで（束ねる場合は計画を示して止まる）通しで進む

`leader-loop` は次の順に進みます。

1. **受け取ったものを1文にする。** 「やりたいこと」「課題」「作りたいもの」のどれとして受け取ったかを、リーダーが
   自分の言葉で1文に直します。ここがずれると以降がすべてずれるためです。
2. **接地する。** 要件を書く前に、調べれば決まる事実（実装の読み取り、設定値、件数など）を調べ、調べた結果を
   残します。
3. **要件化して、説明して、納得を得る。** 受け入れ条件をインラインした要件のドラフトを作り、**そう解釈した
   理由**を添えて説明します。**ここが唯一のゲートです。** 受け入れ条件が書けないものは、ここで止まります。
4. **設計する。** 本体の `yosage-dev-harness:grounded-design` の接地の規律に従います。
5. **案を出す。** 複数案を出したあと、依拠している制約を列挙し、各制約を外した場合の案を書きます（書けない
   なら、外せない根拠を書きます）。
6. **裁定は随時。** 判断が出たら、その場で調べる、前例を引く、人へ上げる、のどれかになります
   （[adjudication.md](adjudication.md)）。
7. **分解する。** 実装できる単位に割ります。割り方の基準は本体の計画スキルが持ちます。リーダーは出来上がった
   計画を監修します。
8. **起票する。** 本体の `yosage-dev-harness:issue-create` の規律に従い、起票の前に重複を検索します。

### 2. ここで止まる（着火は人が引く）

**`leader-loop` は起票で終わります。実装の着火はしません。** 起票したあと、リーダーは「次に人が引くべき
トリガ」を、貼ればそのまま動くコマンドの形で示します。主に想定するのは**単発の issue** で、次の形です。

```text
/yosage-dev-harness:issue-implement <owner>/<repo>#<N>
```

Epic のような**束ねた一括起票**は、段階0の範囲外です（[authority.md](authority.md)）。リーダーは起票の手前で止まり、
計画（分解の案）を人に示して、次のトリガを案内します。計画を書くのは `epic-create-docs`（分解の案を `<概要>` に渡します）、一括起票は人だけが起動
できる `epic-create-issues` です。

```text
/yosage-dev-harness:epic-create-docs <epic-name> <概要>
/yosage-dev-harness:epic-create-issues <epic-title>
```

起票したあとは、次の形で本体の Epic の実装を人が起動します。

```text
/yosage-dev-harness:epic-implement <owner>/<repo>#<N>
```

現在の段階0では、権限の線（[authority.md](authority.md)）と、本体のルール `implement-routing` の「着火が重い
遷移は人がトリガする」の両方が、人による着火を求めています。段階1・2を開けるのは、人が着火を明示して委譲した
ということです。段階の表を開ける構成変更と、導入先の profile への本体が定める委譲の宣言の両方を行ったときだけ、メインが単発の issue（Epic に属さない
もの）の着火をしてよくなります。Epic の Sub-issue の着火は、段階を開けても人が引きます（詳しくは
[authority.md](authority.md) の「段階1・2と本体のルール」）。

### 3. 着火のあと

人が着火を指示したあとの流れは、本体の流れ（実装役への投入、draft PR、一次レビュー）です。リーダーはその間、
次の役を担います。

- **投入の計画と指示を書く。** 複数の issue があれば、ウェーブに分けて順序を決めます（`work-sequencing`）。
  実装役へ渡す指示は、`dispatch-instruction` の項目に沿って書きます。
- **完了を「実装が終わった」ではなく「レビューを経て受け入れ可能になった」と捉える。** 実装役はレビュー前の
  状態で止まり、レビューの差配と受け入れ判断はリーダーが行います。
- **マージを推奨するか保留するかを述べる。** マージ可能な状態になり、自分の検証が終わった時点で、PR の
  コメントに、推奨か保留か、理由、何をもって検証したか、残っている懸念、どの状態（コミット）に対する
  表明かを書きます。表明するだけで、**実行はしません。**
  修正が入って状態が変わったら、既存のコメントを編集せず、新しいコメントとして出し直します。

### 4. 人がマージする

マージは人が自分の手で行います。リーダーのマージ推奨は、人の判断材料です。人は、推奨をそのまま受けても、
食い違う判断をしても構いません。食い違ったときは、その理由が次の前例になります。

## 人が判断する場面

通しの流れの中で、人が関わるのは次の場面です。

| 場面 | 人がすること |
|---|---|
| 要件化ゲート | 受け入れ条件と、そう解釈した理由を読んで、納得するか差し戻す |
| 着火 | 起票された作業を実際に走らせるかを決め、トリガを引く |
| マージ | PR とリーダーの推奨を見て、自分の手でマージする |
| 止まる条件に当たったとき | リーダーが「どこまで進んだか」と「何が判断を要するか」を書いて止まる。それに答える |
| 前例が無い裁定 | 価値のトレードオフなど、調べても前例でも決まらないものを裁く（[adjudication.md](adjudication.md)） |

止まる条件に当たる回数が多く、定常の接点のようになっているなら、通しで進める設計が合っていません。
その場合は工程の区切りを入れ直す、というのがこの拡張の見直しの条件です。
