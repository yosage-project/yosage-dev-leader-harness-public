# 裁定と前例

「裁定」は、価値のトレードオフ、決めないと進めない未決の問い（blocking な Open Question）、例外の扱い、
レビュー指摘のトレードオフ、実装中に前提が崩れたときの再判断などを、誰がどう決めるかのことです。
リーダーは判断を下す前と下した後に、`yosage-dev-leader-harness:adjudication-capture` を読み込んで従います。

目的は、人の裁定を**前例として貯め**、前例のある種類の判断から順にリーダーが引き受けていくことです。人に
上げる件数を、質を落とさずに減らしていく仕組みです。

## 上げる前の3段

判断が出たら、人に上げる前に次の順で確かめます。

1. **調べれば決まるか。** 手元のデータの集計、実装や設定の読み取り、1コマンドを実行してみること、外部の
   公式文書を読むこと、で答えが出るものは**調べます。人に上げません。** ただし「調べて決めた」ことと、
   決まった事実を報告に明記します（人が覆せるようにするため）。
   調べても決まらないものは、価値のトレードオフ、その人しか持たない前提（他チームの都合など）、将来の意向です。
2. **前例があるか。** 本体の `yosage-dev-harness:recall-knowledge` で、同種の判断の前例を引きます。
   **直接適用できる前例があれば、リーダーが裁定して先へ進みます。** 前例を適用した旨と前例の要旨を報告に明記
   します（ここでも人が覆せます）。
3. **前例が無い、または確信が持てなければ、人へ上げます。** 迷ったら上げる側に倒します。

調べずに上げると、人も情報が足りないまま判断することになり、「それは調べれば分かるのでは」と指摘する手間まで
人が払うことになります。そのため、調べる段が先に置かれています。

## 上げても質が上がらない判断

規律・知見・プロンプトそのものの変更は、読んでも良否が見えず、動かしてみないと分かりません。上げられた人も
同じ制約の下にあるので、上げても判断が良くなるとは限りません。実測でも、こうした変更の中身はほぼ検分されて
いません。

それでも、これらは**上げます**（権限の線で、リーダーが自分で変えない対象だからです。[authority.md](authority.md)）。
上げることで判断が良くなる、という理由ではないので、「前例が貯まれば自動化できる」とは読めません。
この性質を、権限の線を開ける根拠に使うこともしません。判断の材料は、入れた後に**実際に何を捕まえたか**を
その場で知見として残し、事後の効果で見ます。

## 大きな判断では、根本案を別の主体に作らせる

人へ上げる判断のうち、次のいずれかに当たるものは、リーダー自身が漸進案と根本案の両方を書かず、**根本案の
生成を別の主体に頼みます**。

- 触る対象が複数のファイルにまたがる
- 規律（スキル）、既存の知見、受け入れゲートの設定のような重い対象を含む
- 不可逆な操作を含む

頼む先は本体の `yosage-dev-harness:architect` で、次の2回に分けます。

1. **症状だけを渡す。** 既存の実装や規律はまだ調べず、ゼロから対処するなら何を作るかを書かせる。診断・根本案・
   書けない場合はその理由、の形で返させる。
2. **既存を読ませて差分を書かせる。** 1の出力を渡し、既存の実装・規律との差分と、既存を維持すべき理由を書かせる。

依頼文には、リーダー自身の結論や推奨案を書きません（見せると根本案がその変形に収束するためです）。

単一のファイルで可逆、局所的な判断は対象外です。

## 人が裁定したら、その場で残す

人が裁定したら、後回しにせず**その場で**、本体の `yosage-dev-harness:capture-learning` で案件の知見に残します。
書く内容は次の3つです。

- 裁定そのもの
- なぜそう裁定したか（人が挙げた理由）
- **反証条件**（何が変われば裁定が変わるか）

反証条件が書けない裁定は、一般化できていません。その場合、リーダーは人に「どういう場合なら逆になりますか」を
聞いて埋めます。セッション内だけで通じる呼び名（「案A」など）は、中身に展開して書きます。このセッションに
居なかった人が、前例として使えるようにするためです。

## 次に引く

次に同種の判断が出たとき、リーダーは手順の2（recall）でこの知見を引き、直接適用できれば自分で裁定します。
適用した旨と要旨を報告するので、人は覆せます。前例が貯まるほど、人に上げる件数が減る、という流れです。

## マージ推奨の食い違いも前例にする

リーダーがマージを推奨（または保留）し、人の判断と食い違ったときは、その**理由**を、表明と同じ PR コメントに、
または裁定として知見に残します。目的は上位の判断を当てにいくことではありません。当てにいくと、正しさでは
なく迎合を学習してしまうためです。食い違いは、判断基準を直す材料として扱います。

なお、次の種類の変更は、委譲が進んでも恒久的に人（上位）に残ります。仕様・設計判断を含む変更、不変条件や
ルール自体を変える変更、受け入れゲートの設定の変更、外部（クライアントや顧客）に見える挙動の変更、戻すのが
高い変更（データ移行・公開物）、他の文脈へ伝播する知識（グローバル昇格候補）です。
