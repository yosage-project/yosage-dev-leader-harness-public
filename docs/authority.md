# 権限の線

リーダーが**人に聞かずにやってよい範囲**と、**止まって人へ上げる条件**です。判断・着火・マージ推奨の前に、
リーダーは `yosage-dev-leader-harness:authority` を読み込んで従います。

線を宣言しておく理由は、宣言が無いと、同じ種類の作業が日によって「自分で進む」「確認を求める」と揺れ、
どちらが正しかったのかも後から分からなくなるためです。宣言があれば、越えたかどうかが事実として判定でき、
線を動かすことが明示の変更になります。

## 線の引き方

権限は「行為 × 対象範囲」で宣言します。

- **対象範囲「内」**: 案件を構成するリポジトリ。単一リポジトリの案件ならそのリポジトリ、ワークスペースなら
  ワークスペースとそこに同居するリポジトリ（成果物・記録・issue / PR）。
- **対象範囲「外」**: それ以外のすべて。他組織のリポジトリ、外部サービス、公開物、課金や契約を伴うもの。
  **外は常に止まります。**
- **配布元への起票は外です。** ハーネス本体・知識ストア・リーダーハーネス自身に問題を見つけても、リーダー
  は「こんな問題があったので報告しますか？」と提案するところで止まります。人が明示して指示したときだけ
  起票します。
- **表に挙がっていない操作は、許可に含まれません。** 許可を列挙して判定し、禁止を列挙して判定することは
  しません（禁止の列挙は取りこぼし、取りこぼしは「止まらない」側へ倒れるため）。

## 段階

現在の設定は**段階0**です。

| 段階 | 人に聞かずにやってよいこと（対象範囲は「内」に限る） | 状態 |
|---|---|---|
| 0 | 要件化、設計、案の生成、調べれば決まる判断と前例で決まる判断、分解、単発 issue の起票、自分が起票したものの取り下げ（クローズ）、知見の新規追加 | 初期値（現在） |
| 1 | 起票済みのうち、自明な小修正の投入着火 | 未開放 |
| 2 | まとまった単位の投入着火 | 未開放 |

段階0に**含まれない**ものの例です（網羅ではありません）。

- 複数の作業単位を束ねたものの一括起票
- 大きい設計討議への入場
- 既存の知見の改廃と、他の文脈へ配る昇格
- 規律そのものの変更（リーダーハーネスのスキルの本文、案件のリポジトリのルールに書いたその規律の適応）
- 他者が起票したものの編集・クローズ、ラベルの操作、レビューの投稿

段階を開けるのは、人（上位）が行う明示の構成変更です。リーダーが黙って緩めることはありません。下げる方向は、
いつでも上位が行えます。

### 段階1・2と本体のルール

段階1・2を開けるのは、人が着火を明示して委譲した、ということです。本体のルール `implement-routing` は実装の
着火を人が引くものと定めており、例外は、導入先の profile（`.claude/rules/<名前>/profile.md`）に本体が定める
固定の1行（「実装の着火の委譲」。書式は本体の `project-profile` ルール）を宣言したときだけです。段階を開ける
ときは、段階の構成変更と、この宣言の記載をあわせて行います。

委譲できるのは、宣言した範囲に入る、Epic に属さない単発の issue の着火までです。Epic の Sub-issue は1件ずつでも
対象外で、人が引きます。

- 段階1（自明な小修正の投入着火）: 単発の issue なら、この宣言で開けられる範囲に収まります。
- 段階2（まとまった単位の投入着火）: Epic の Sub-issue に当たる着火は、段階2を開けても人が引きます。「まとまった
  単位」の範囲をどう取るかは、段階2を開ける判断の時点で決めます（現時点では決めていません）。

## 止まる条件

次のいずれかに当たったら、リーダーは**そこで止めて報告します**。自分で先へ進みません。

1. 段階の表に無い操作が要るとき。
2. 対象範囲が「外」に及ぶとき。
3. 触る対象が、規律、**既存の**知見（改廃・他の文脈への昇格）、受け入れゲートの設定のいずれかのとき。
   知見の**新規追加**は止まりません。判定は「判断の性質」ではなく「触る対象と操作」で行います。
4. 要件の受け入れ条件が書けないとき。

止まるときは、**どこまで進んだか**と**何が判断を要するか**を書きます。「判断を待ちます」だけでは、受け取った
側が状況を組み立て直すことになるためです。

## 人が関わる定常の接点

止まる条件とは別に、段階0の通しの進行の中で、上位の応答を待つ定常の接点が2つあります。

- **要件化ゲート**（人）: 受け入れ条件つきの要件と、そう解釈した理由を説明し、納得を得る。
- **着火**（上位）: 起票した作業を実際に走らせる判断。

これに、止まる条件に当たったときが加わります。「接点は2つだけ」とは言えません。

## 通しで進んでよい理由

要件化のあと、設計・案の生成・裁定・分解・起票までは、工程ごとに区切らず通しで進みます。区切っても裁定が
承認に変わるだけで、人が挟まる回数は減らないためです。

ただし、通しの区間は取り消せない出力を生みます。issue の起票は取り下げられますが、番号と通知は残ります。
知見の追加は、将来の前例の原料になります。接地のための実行は、副作用が出ることがあります。これらは**受容して
います**。いずれも対象範囲の内に閉じており、誤りが残っても、次の判断の材料として読める形で残るためです。
この受容は段階0に固有で、着火まで開けた段階では根拠を立て直します。

## 越えてしまったとき

越えたことに後から気づいたら、リーダーは**復旧を自分で判断せず、報告して止まります**。越えた事実も報告に
含めます。

この宣言が担保できるのは、**正直に申告された越境だけ**です。実行するのも報告するのも同じ主体なので、報告
されなかった越境はどこにも現れません。これは限界として明記されています。

## 案件ごとに変えたいとき

導入先に規律のコピーは置かれないので、案件固有の適応は、案件のリポジトリのルール（`.claude/rules/` 等）に
書きます。ただし、規律の適応を書き換えることは、それ自体が止まる条件（規律の変更）にあたります。リーダーが
提案し、人が決めます。
