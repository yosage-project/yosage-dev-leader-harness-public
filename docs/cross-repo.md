# 複数のリポジトリにまたがる案件

実装役は、割り当てられた1つのリポジトリの中で完結します。リーダーはそうではありません。1つのセッションの中で、
知見を案件側の記録に残し、実装を案件のリポジトリ（ワークスペースなら各メンバーのリポジトリ）へ投入し、
学びを配布元へ提案する、というように、複数のリポジトリへの書き込みを行き来します。

事故が起きやすいのは、**別のリポジトリの作業へ移る瞬間**です。この拡張は、その瞬間のための作法を
`yosage-dev-leader-harness:cross-repo-operations` にまとめています。

## いつ適用されるか

**このセッションで2つ目のリポジトリへ書き込もうとするとき**に、書き込む前に適用されます。書き込みには
コミット、push、issue / PR の作成、コメントの投稿が含まれます。

- 案件の形（単一リポジトリかワークスペースか）では判定しません。単一リポジトリの案件でも、人の指示で配布元へ
  起票するなら、リポジトリをまたぎます。
- ワークスペースでも、1つのリポジトリにしか書かないセッションには適用されません。
- 迷ったら適用します。作法は、1つのリポジトリの中で守っても害がありません。

## 書き込む前の作法

別のリポジトリへ切り替えた直後や、複数のリポジトリを行き来している最中の git 操作では、次を守ります。

- **git 操作の対象リポジトリを明示する。** 作業ディレクトリが対象を指しているかを、操作の前に確認する。
- **一括ステージを使わない。** 変更したファイルを個別に指定してステージする。
- **コミット前に、ステージした内容の件数を見る。** 想定した変更の桁と食い違っていたら、進めずに止める。
- **安全網の適用範囲を確認する。** 「フックがあるから大丈夫」は、今コミットしようとしているそのリポジトリに
  フックが入っているかを見てから言う。別のリポジトリで確認した安全網は、この操作には効きません。

これらは機構による強制ではなく、**作法**です。

## 配布元への起票は提案から

ハーネス本体、知識ストア、リーダーハーネス自身といった配布元への起票は、リーダーが通常の行為として行いません。
「こんな問題があったので報告しますか？」と提案するところで止まり、人が明示して指示したときだけ起票します
（[authority.md](authority.md) の対象範囲「外」）。

## 実装役に別のリポジトリを触らせるとき

リーダー自身の書き込みの作法とは別に、**実装役に、割り当てた作業領域のリポジトリとは別のリポジトリを触らせる**
ときは、投入指示（`yosage-dev-leader-harness:dispatch-instruction`）に次を足します。絶対パスを書くだけでは、
そのパスがどのリポジトリの作業ツリーかも、対象リポジトリがその配下にあるかも、指示から分かりません。

- 対象リポジトリが、割り当てた作業領域の配下にあるかを明示する。
- 配下に無いときは、共有のチェックアウトを参照しない取得手段（たとえば、割り当て領域の配下へ独立に `clone`
  する）を指示に含める。
- 本体の安全機構（guard）は、worktree で隔離した実装役が Bash で打つ git 操作のうち、共有チェックアウトなど
  割り当て領域の外を指すものを、`git log` のような読み取りだけの操作でも遮断します。作業ディレクトリが割り当て
  領域の配下のときに働く best-effort の網で、Read / Grep ツールは通します。これを前提に書く。

あわせて、どの指示にも「割り当てた領域の配下か確かめてから編集する」「万一外れたら自分で復旧せず、報告して
止まる」を書きます。

## 事故に気づいたら

意図しないリポジトリへの書き込みや、機微情報の流出に気づいたときの作法です。

1. **まず報告する。** 対応の実行より先に、検知した事実を人へ伝える。
2. **証跡に触れる操作（削除、クローズ、履歴の書き換え）は、指示を待つ。** 露出を止めたくなりますが、独断で
   行うと、原因調査や影響範囲の特定に使える証跡そのものを動かしてしまいます。

## push したものは回収できない

一度 push したコミットは、ブランチを削除しても消えません（プルリクエストの参照が保持します）。amend や
force push でも、リモートに渡った内容を無かったことにはできません。回収できるという前提で操作しないでください。
最も確実な事故防止は、push する前の段階、つまり上の作法にあります。
