# リポジトリ横断操作とインシデント対応（リーダー運用・不変条件）

> リーダーハーネス（プラグイン `yosage-dev-leader-harness`）の規律。導入先には写さず、プラグインのスキルとして
> 読み込む。案件ごとの適応は、案件のリポジトリのルール（`.claude/rules/` 等）に書く。一般化する価値のある変更は、
> 利用者に報告を提案する（利用者が明示して指示したときだけ配布元へ起票する。導入先の利用者は、配布元が用意する報告の窓口へ）。

## 適用条件

**このセッションで2つ目のリポジトリへ書き込もうとするとき（書き込む前に読む）**に適用する。書き込みには
コミット・push・issue / PR の作成・コメントの投稿を含む。事故が起きるのは2つ目に最初に書く瞬間なので、
書き込んだ後ではなく前から適用する。案件の形（単一リポジトリか、ワークスペースか）では判定しない——
単一リポジトリの案件でも、利用者の指示で配布元（ハーネス本体・知識ストア等）へ起票するなら
リポジトリをまたぐ。ワークスペースでも、1つのリポジトリにしか書き込まないセッションには適用しない。

迷ったら適用する側に倒す（作法はどれも、1つのリポジトリの中で守っても害が無い）。

## リーダーは複数リポジトリへ書き込みうる

実装フラクタル（割り当てられた1つの担当範囲に閉じて作業する主体）は、1つのリポジトリの中で完結する。
リーダーはそうではない——**1つのセッションの中で、知見を案件側の記録へ残し、実装を案件のリポジトリ（ワークスペースなら各メンバーのリポジトリ）へ
投入し、学びを配布元へ起票する（提案し、利用者が指示したときだけ）、という複数リポジトリへの書き込みを行き来する**。この違いは次の3点に表れる。

| | 実装フラクタル | リーダー |
|---|---|---|
| 触るリポジトリ | 割り当てられた1つ | 複数になりうる（案件を構成するリポジトリ・利用者の指示で起票する配布元） |
| 作業の切り替え | 起きない | 頻繁に起きる |
| 安全網の適用 | 担当リポジトリに効く | リポジトリごとに有無が違う |

**「別のリポジトリの作業へ移る瞬間」が事故の特異点である**。実装フラクタルにはこの遷移が構造的に存在
しないため、実装フラクタル側の規律をそのまま適用しても、この遷移そのものへの防止策にはならない。

## 配布元への起票は提案から始める

配布元（ハーネス本体・知識ストア・リーダーハーネス自身）への起票は、通常の行為として自分では行わない。
問題を見つけたら「こんな問題があったので報告しますか？」と提案するところで止まり、利用者が明示して
指示したときだけ起票する（範囲の定義は 「`yosage-dev-leader-harness:authority` スキル」の対象範囲）。

## repo をまたぐときの作法

別のリポジトリへ切り替えた直後、または複数のリポジトリを行き来している最中の git 操作では、次を守る。

- **git 操作はリポジトリを明示する**。作業ディレクトリが対象のリポジトリを指しているか、作業ディレクトリの
  暗黙状態に依存せず、操作の前に確認する。
- **一括ステージを使わない**。変更したファイルを個別に指定してステージする。
- **コミット前にステージ内容の件数を見る**。想定していた変更の桁と食い違っていたら、そのまま進めず止める。
- **安全網の適用範囲を確認する**。「フックがあるから大丈夫」という判断は、**今まさにコミットしようとして
  いる、そのリポジトリにフックが入っているか**を見てから行う。別のリポジトリで確認した安全網は、この
  操作には効かない。

これらは機構による強制ではなく**作法**である。コミット内容の走査・大量ステージの遮断といった機構は
実装フラクタル側のハーネスが別途担う領域であり、本ルールはリーダー側の作法だけを定める（機構が無くても
守れる作法として書く）。

## インシデント時の作法

事故（意図しないリポジトリへの書き込み・機微情報の流出等）を検知したら:

1. **まず報告する**。対応の実行より先に、検知した事実を人間へ伝える。
2. **証跡に触れる操作（削除・クローズ・履歴の書き換え）は指示を待つ**。露出を止めたい衝動は自然だが、
   独断でそれらの操作を行うと、事後の原因調査・影響範囲の特定に使える証跡そのものを動かしてしまう。
   受け入れ（マージ）の実行を上位フラクタルが行うのと同じ理由で、**インシデント対応の中でも取り返しの
   つかない操作は人が引く**。

## 「push 済みは回収できない」という前提を持つ

一度 push したコミットは、ブランチを削除しても消えない（プルリクエストの参照が保持し続ける）。amend や
force push でも、リモートに一度渡った内容を無かったことにはできない。**回収手段があるという前提で操作
しない**——この認識自体を規律として持つ。したがって最も確実な事故防止は、push した後の後始末ではなく、
push する前の段階（上記「repo をまたぐときの作法」）にある。
