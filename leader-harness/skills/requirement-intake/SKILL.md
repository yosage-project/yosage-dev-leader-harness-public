# 要件取り込み（リーダー運用・不変条件）

> リーダーハーネス（プラグイン `yosage-dev-leader-harness`）の規律。導入先には写さず、プラグインのスキルとして
> 読み込む。案件ごとの適応は、案件のリポジトリのルール（`.claude/rules/` 等）に書く。一般化する価値のある変更は、
> 利用者に報告を提案する（利用者が明示して指示したときだけ配布元へ起票する。導入先の利用者は、配布元が用意する報告の窓口へ）。

クライアント/PO の発話・要望を、**受け入れ条件をインラインした self-contained な要件**へ変換してから
実装フローに流す。受け入れ条件の明文化は、成果物の受け入れ評価（将来の評価フラクタル）と
マージ委譲の前提であり、ここを飛ばすと後段が全部成立しない。

## 手順
1. **ドラフト変換**: 発話・要望を受けたら、リーダーが「背景＋要件＋受け入れ条件（検証可能な形）」の
   ドラフトに変換する。受け入れ条件は「満たした/満たさないが機械的または一目で判定できる」粒度まで落とす。
   **どの構成で観測されるかまで書く**（下記）。
2. **クライアント確認**: ドラフトの受け入れ条件をクライアントに提示し、**受け入れ条件の合意**を取ってから
   確定する（要件本文の言い回しではなく、受け入れ条件こそが合意対象）。
3. **issue 化**: 確定した要件は issue として起票し（self-contained・issue-first の既存規律に従う）、
   実装フロー（レーン分類→dispatch）へ流す。
4. **受け入れ条件が書けない要望**は blocking OQ として扱い、確定させないまま実装に流さない。

## 受け入れ条件は「どの構成で観測されるか」まで書く

「コードが X する」ではなく「**どの構成で動かしたとき X が観測されるか**」を条件に書く。

理由は、**受け入れ条件が実装と同じ理解から書かれる**ため。同じ理解から出た条件を同じ理解で作った実装が
満たしても、**両者が共有している盲点は検出できない**。実際に動かした結果だけが、その理解の外側から来る入力になる。

特に、**個別には正しい2つの実装が接する継ぎ目**（自前のコードとフレームワークのエラー処理、
複数サービスの同時起動、生成物と消費側の期待）には仕様が存在しない。両側がそれぞれ自分の側だけを
記述しているため、設計レビューや仕様の読み合わせでは原理的に見つからない。

- 統合された構成での確認が本質的な要件では、**その確認を受け入れ条件として明示**する。書かなければ、
  実装者は孤立した構成での確認で条件を満たしたとみなす（条件の文面上はそれで正しい）。
- 全ケースを統合構成で確認させる必要はない。**1件あれば「配線が成立している」ことは固定できる**。
- 統合構成での確認コストが極端に高い場合（実機や本番でしか再現しない条件）は、
  **未検証である事実を条件の中に残す**（暗黙に検証済みとして扱わない）。

## 分解を監修する（要件 → 実装計画）

要件が確定したあと、**それを実装可能な単位へ割る工程**がある。**割り方の基準そのものは実装フラクタル側の
計画スキルが正本**であり、ここでは再記述しない（基準が2箇所にあると drift する）。

リーダーが担うのは**監修**——出来上がった計画を、次の観点で照らす。いずれも「**何を見落とすと何が起きるか**」
の形で書く。チェックリストとして通過儀礼にしない。

### スコープの縁の帰結を、計画にも要求する

**「含めないものと、それを落とした場合の帰結を書く」という要求そのものは再記述しない**（投入指示の型
＝「`yosage-dev-leader-harness:dispatch-instruction` スキル」 が持つ）。リーダーが足すのは**適用先**——同じ要求を、
作業者へ渡す指示だけでなく**分解の計画にも課す**こと。

計画の側で帰結が書かれていないと、**縁の妥当性を判断できない**まま各単位へ割られる。実例では、「今は
入れない」と決めた要素について後続で既存のファイルを触り直すことが分かっており、それを書いたことで上位が
「それなら今入れる」と判断し直せた。**帰結を書かせなければ、その判断の機会自体が生まれない。**

### 未決の二分を、計画の段階で済ませておく

**二分の基準そのものは再記述しない。** 実装フラクタル側の入口ゲート（ルール `implement-routing`
の「実装入口 OQ ゲート」節）が既に定義しており、そこが正本である。

リーダーが足すのは**時点**だけ——**その二分を、投入の直前ではなく計画の段階で済ませておく**こと。

**投入の直前まで先送りすると、そこで初めて「これは着手前に決めないと投入できない」と判明する。** その時点で
計画ごと差し戻すことになり、分解の前提が変わるため**割り直しになる**。計画の段階で二分してあれば、投入は
確認だけで済む。

### 起票の前に、issue 本文を変える未決を潰す

**上の節が要求しているのは二分を済ませることまでで、いつ解決するかは別の話である。** 解決の時点を
定めているのは実装フラクタル側の入口ゲートだが、そこは**dispatch 前**を指す。Epic は起票 →（人間
トリガ）→ dispatch の順に進むため、**起票と dispatch の間に blocking が未解決のまま残る区間が生まれ**、
どちらの規律もカバーしていない。**この区間を埋めるのはリーダーである。**

起票の前に、次の基準で潰すものを選ぶ。

> **その未決の結論で、issue 本文（対象ファイル・実装内容・受け入れ条件）が変わるか。**
> **変わる**なら起票の前に潰す。**変わらない、または実測でしか決まらない**なら、issue に仮定として
> 記録して起票してよい。

**判定は「self-contained に書かれた issue 本文」に対して行う**（起票の規律が要求する形——背景と
受け入れ条件をインラインし、受け入れ条件を検証可能な粒度まで落とした状態。基準は起票の規律が正本）。
**書き方を粗くすれば何も変わらないので、粗い下書きに対して判定すると常に「変わらない」になる。**

**本文が変わらなくても潰すものが1つある**——**共有される決定**（この計画が分割した複数の単位にまたがる
もの）。受け入れ条件を振る舞いの水準で書けば本文は変わらないが、**後から変えると分割した単位すべてへ
波及する**（例: 同期で組むか非同期で組むかを最初の単位の実装に委ねると、後で覆ったときに他の単位も
書き直しになる）。**共有される決定は、本文が変わらなくても起票の前に潰す。**

**「共有される」の範囲は、この計画が分割した単位に限る**（起票済みかどうかは問わない）。計画に現れて
いない将来の追加は含めない——含めると範囲が定まらず、あらゆる設計判断が対象になる。
**判定の基準は、起票の直前に確定している分解**とし、分解を組み替えたら判定をやり直す
（組み替えの途中では、どちらの分解を基準にするかで分類が変わるため）。

**潰せないものは潰せない。** 実測でしか決まらない未決（環境での適用手順・生成物が既存と同じ出力に
なるか・複数の単位が使う設定値で動かさないと決まらないもの等）を起票前に潰そうとすると、**実装に
入らないと起票できない**という循環になる。**共有される決定であっても、実測でしか決まらないならこちらが
優先する**（起票を止めない）。

**その場合は起票を止めず、依存を issue の仮定として明示して起票し、順序は dispatch の側で受ける**
（依存関係でウェーブを分ける仕組みは投入計画の規律が持つ。ここでは再記述しない）。**起票を待たせない**
のは、起票フェーズを先行単位の実装完了まで直列化させると、Epic が起票をまとめて済ませてから dispatch
するという前提そのものを壊すためである。

**入口ゲートの基準との関係**: 入口ゲートの blocking は**複数の条件のいずれか**で成る（**条件の定義は
入口ゲートが正本。ここでは列挙しない**）。ここで足すのは、**そのうちどれが起票の時点でも効くか**という
対応づけだけである。

- **実装する物が変わる**という条件に**重なりを持つが同一ではない**——判定の対象が「実装する物」ではなく
  「**起票する文**」であり、実装が変わらなくても本文が変わることがある。
- **戻しにくさ**の条件は、上記の**共有される決定**という形でだけ効く。単位が1つに閉じるなら、戻しにくい
  未決でも起票する文が変わらなければ起票してよい。
- **前例の有無**は起票の時点では使わない。

**入口ゲートの判定自体は dispatch 前の工程としてそのまま残る**（起票の時点の判定がそれを置き換えない）。

**起票してから解決すると、起票した issue が一度も正しくない状態を経由する**（書き換えが要る・その時点の
issue は self-contained でもない）。実例: ある移植の計画で Sub-issue 10 件まで固めたが、名称の綴りを正すか
と基底クラスの拡張方法の2件は**結論が出るまで本文を確定できない**性質で、どちらも「記録してあるから起票
してよい」と扱っていた。

### ツーリング由来の順序制約を先に洗わせる

**実行環境やハーネス自身の仕組みが、計画の順序を縛ることがある。** 実例では、あるファイルを置いた瞬間から
ホストでの特定コマンドの実行が遮断される仕組みがあり、それを知らずに順序を組むと「置いた直後に検証手段が
無い」区間が生まれるところだった。

環境やツールが課す制約は、**要件にも設計にも書かれていない**。計画時に能動的に洗う必要があるが、その視点
自体が抜けやすい。

### 参考実装から借りるのは「型」であって固有の選択ではない

似た構成の先行事例を参照するとき、借りてよいのは**構造の型**であり、言語固有・案件固有の選択ではない。

**線引きを書かせないと、固有の選択が「前例がある」という理由で通る。** 参照元では正しかった判断が、こちらの
制約の下では正しいとは限らないが、**借りた事実が記録されていなければ、その差を問う契機が無い**。どこまでが
型でどこからが固有かは都度の判断になるため、**計画に「どこを借りたか」を書かせて、その線引きを監修の対象に
する**。

### 計画が対話で固まった場合、後追いで書き起こす

方針が**対話の中で固まる**ことがある。分割の軸・スコープ・受け入れ条件まで会話で決まり、そのまま issue の
起票へ進む——この経路では**計画そのものが記録として残らない**。

**issue には書けない情報がある。** なぜその軸で分割したか・落とした別案とその理由・スコープ外にしたものが
必要になる契機・未決事項・横断ルールから逸脱した箇所とその裁定の出どころ。issue は作業単位として
self-contained に書くため、これらは載らない。**行き場が消える。**

結果として、**後から「なぜこうなっているのか」を復元できない**。同種の計画が再来したとき、同じ検討を
一からやり直す。

**対話を禁じるのは解ではない**（方針を固める正当な手段である）。対話で固まったものを、**後追いで書き起こす**。

書き起こすのは**対話の文脈を持っている主体**である。通常それはリーダーであり、**文脈を持たない主体に
書かせると、issue に書けない情報が失われた状態のものができる**——それでは書いた意味がない。

**不在の検出は実装フラクタル側が機械的に行う**（配置とその理由は `yosage-dev-harness:epic-implement` スキル
が正本。ここでは再記述しない）。リーダーが担うのは**検出されたものを書き起こすこと**だけであり、
**検出する側は中身を作れない**——この分離が要点である。

**発注先が別組織で、計画を相手方のリポジトリに置けない構成では、これが唯一の計画の記録になる。**
その場合、書き起こさなければ計画そのものが残らない。

なお「文脈を持つ主体でなければ書けない」が成立するのは、**対話の内容が後から復元できない場合**である。
やり取りが完全に保存され読み直せるなら、別の主体でも書き起こせる——その環境ではこの制約は緩む。

### 反証条件（何が変われば分解の監修を見直すか）

- **上記の観点が実装フラクタル側の計画スキルへ内蔵された場合** — 該当観点はここから落とす（再記述は drift）。
- **観点を照らしても分解の誤りが減らない場合** — 監修という形が効いていないことになるので、別の受け方
  （計画そのものを別主体が作る等）を検討する。
- **起票前に潰す運用にした結果、起票そのものが進まなくなった場合** — 判定基準（issue 本文が変わるか）が
  広すぎる。線引きを見直す。
- **起票後の blocking 解決が、実際には issue 本文の書き換えを伴わなかった場合** — 前提（結論が本文を
  変える）が成立していないので、起票前に潰す要求の必要性を問い直す。
- **実装フラクタル側の入口ゲートが起票の時点もカバーするよう変わった場合** — リーダー側で起票前に
  潰す要求は不要になる（重複した規律になるため落とす）。

## 評価差分・顧客の声の還流
- クライアントの受け入れ評価で出た差分（「ここが違う」）は、会話で受け流さず **issue 化**して
  次サイクルの入力にする。
- 顧客の声・ドメイン知見は案件 knowledge（固有 domain）へ capture し、以後の設計判断の recall 対象にする。
- 判定基準:「クライアントが同じことを二度言わなくて済むか」。
