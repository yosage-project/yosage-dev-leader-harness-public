# 権限の線（リーダー運用・不変条件）

> リーダーハーネス（プラグイン `yosage-dev-leader-harness`）の規律。導入先には写さず、プラグインのスキルとして
> 読み込む。案件ごとの適応は、案件のリポジトリのルール（`.claude/rules/` 等）に書く。一般化する価値のある変更は、
> 利用者に報告を提案する（利用者が明示して指示したときだけ配布元へ起票する。導入先の利用者は、配布元が用意する報告の窓口へ）。

リーダーが**人間に聞かずにやってよい範囲**を宣言し、越えたときの振る舞いを定める。

他の規律は「どう判断するか」（「`yosage-dev-leader-harness:adjudication-capture` スキル」）「どう投入するか」
（「`yosage-dev-leader-harness:work-sequencing` スキル」 /
「`yosage-dev-leader-harness:dispatch-instruction` スキル」）を扱う。本ルールが扱うのは**どこで止まるか**だけ。

## なぜ宣言が要るか

権限の線を書かずに運用すると、**線が判断のたびに引き直される**。同じ種類の作業が、ある日は
自分で進み、別の日は確認を求める。どちらが正しかったのかは後から判別できず、**線が動いたこと
自体が記録に残らない**。

宣言してあれば、**越えたかどうかが事実として判定でき**、線を動かすことが**明示の変更**になる。

## 権限は「行為 × 対象範囲」で宣言する

**行為の列挙だけでは線にならない。** 同じ操作でも、触る対象が変われば戻しにくさが変わる。

### 列挙外は留保する（この規則が土台）

**段階の表に挙がっていない操作は、段階に含まれない。** 許可を列挙して判定し、禁止を列挙して
判定しない——**禁止の列挙は必ず取りこぼし、取りこぼしは「止まらない」側へ倒れる**。

判断に迷う操作が出たら、**表に無いという理由で止まる**。表へ足すのは下記「段階を開ける判断」に従う。

### 対象範囲

| 範囲 | 中身 |
|---|---|
| **内** | 案件を構成するリポジトリ——単一リポジトリの案件ならそのリポジトリ、ワークスペースならワークスペースとそこに同居するリポジトリ（成果物・記録・issue / PR） |
| **外** | 上記以外のすべて。他組織のリポジトリ・外部サービス・公開物・課金や契約を伴うもの |

**外は段階に関わらず常に停止する。** 段階は内の中でだけ動く。

**配布元（ハーネス本体・知識ストア・リーダーハーネス自身）への起票は、案件の形によらず外。** 問題を
見つけたら報告を提案する（「こんな問題があったので報告しますか？」）ところで止まり、利用者が明示して
指示したときだけ起票する。導入先の利用者には、配布元が用意する報告の窓口（フィードバック用フォーム）を
案内する。

## 主体（誰がこの規律の各役割を持つか）

対象範囲＝どこを触るか、に対して、本節は**誰が各役割を持つか**を宣言する。規律は一段上の主体を
`人間` と `上位` の2語彙で呼んでおり、片方（`人間`）は「一段上が人である」という前提を焼き込んで
いた。フラクタルを積む方向では一段上はエージェントになりうるため、役割ごとに移譲してよいかを
判定し、判定に応じて使う語を固定する。

**置き換えてよいかは「上位しか判断できないか」で切る。** 問1「その役割は、上位にしか存在しない
情報の出どころか」（要件・意図・優先順位・外部からの観測）。問2「その役割は、移譲先が属している
系そのものを制約しているか」（規律の変更・自己監査）。**どちらも No なら階層上の位置にすぎず、
移譲できる。**

| 役割 | 判定 | 使う語 |
|---|---|---|
| 要件化ゲート | 上位固有の情報源 | `人間` |
| 抜き取り検分 | 系外性が要る | `人間` |
| 規律・知見の変更の裁可 | 同じ系の中へは不可（系をまたげば可） | `上位` |
| 着火 | 位置のみ | `上位` |
| 受け入れ（マージ） | 位置のみ | `上位` |

**各行の判定理由**:

- **要件化ゲート**（問1: Yes）— 要件・意図・優先順位は、上位にしか無い情報の出どころである。
  この役割を移すと、聞く役が作る役に入れ替わってしまう（移譲ではなく捏造にあたる）。
- **抜き取り検分**（問1: Yes・問2: Yes）— 抜き取り検分（上位が成果物そのものを直接見ること）が
  唯一の外部からの入力であり、**行われない期間が続けばこの工程は自己参照だけで閉じる**。
  同じ系の中の主体が代わりに回しても、書き手と共有している盲点は検出されない。
- **規律・知見の変更の裁可**（問2: Yes・同じ系の中は不可）— 同じ系の中の主体へ移すと、下記
  「この宣言が担保できないこと」が既に認めている「提案して素通り承認される経路は、実質的に
  自分で自分の制約を緩められる」がそのまま戻ってくる。系をまたいだ主体（別の系に属する上位）へ
  移すことまでは妨げない。
- **着火**（問1: No・問2: No）— 起票済みの作業を実際に走らせる判断であり、上位固有の情報も
  系の自己制約も持たない。階層上の位置にすぎず、移譲できる。
- **受け入れ（マージ）**（問1: No・問2: No）— 一見「欲しかったものを満たしているか」の判断に
  見えるが、「`yosage-dev-leader-harness:requirement-intake` スキル」 が受け入れ条件を「満たした/満たさないが
  機械的または一目で判定できる」粒度まで落とすことを既に要求している。**書き出された瞬間に、
  判定の出どころが上位の頭の中から成果物へ移る**。したがって階層上の位置にすぎず、移譲できる。
  **委譲そのものの具体的な条件**（実際にいつ・どういう基準で委譲するか）は本節では定義しない
  ——委譲そのものの条件は案件外の役割定義が正本である。

新しい語は作らない——使う語は既存の `一段上のフラクタル` / `上位` と、上表の4つの判定語
（`上位固有の情報源` / `系外性が要る` / `同じ系の中へは不可（系をまたげば可）` / `位置のみ`。
うち `位置のみ` は着火・受け入れ（マージ）の2行で使う）に限る。

## 段階（初期は0）

| 段階 | 人間に聞かずにやってよいこと（対象範囲は「内」に限る） | 状態 |
|---|---|---|
| **0** | 要件化・設計・案の生成・**調べれば決まる判断と前例で決まる判断**・分解・**単発 issue の起票**・**自分が起票したものの取り下げ（クローズ）**・知見の**新規**追加 | 初期値 |
| 1 | 起票済みのうち、自明な小修正の投入着火 | 未開放 |
| 2 | まとまった単位の投入着火 | 未開放 |

**段階0に含まれないもの**（列挙外は留保、の適用例。網羅ではない）:

- **複数の作業単位を束ねたものの一括起票**（実装フラクタル側の規律が、これを人間がトリガする
  重い遷移として名指ししている）。
- **大きい設計討議への入場**（同じく、実装フラクタル側の規律が人間の承認を要求している）。
- **既存の知見の改廃と、他の文脈へ配る昇格**（新規追加とは戻しにくさが違う）。
- **規律そのものの変更**（リーダーハーネスのスキルの本文、および案件のリポジトリのルールに書いたその規律の適応）。
- 他者が起票したものの編集・クローズ、ラベルの操作、レビューの投稿。

**段階0は、既存の不変条件を1つも破らない**——重い遷移の着火は人間が引く、規律そのものの変更は
上位が持つ、受け入れ（マージ）は一段上が行う。**この主張は、実装フラクタル側の横断ルールが
「人間がトリガする」と名指ししている遷移を実際に列挙して確かめたものである**（その結果、
一括起票と大きい設計討議への入場を段階0の外へ出した。**確かめる前の版では、この2つが
段階0に含まれてしまっていた**）。

**この「重い遷移の着火」は、上記「主体」節の `着火` 行とは別スコープである**——「主体」節が
判定しているのは個別に起票済みの作業を走らせる着火（下記「段階を開ける判断」が扱う段階1/2の
対象）であり、一括起票・大きい設計討議への入場のような重い遷移は、実装フラクタル側の
横断ルール（別リポジトリ・本 PR の対象外）が現に `人間` に限定して定めている。ここを `上位` へ
書き換えると、その外部規律の実際の記述と食い違う——**役割としての着火の語彙（`上位`）ではなく、
現に誰がその位置に居るかを述べている箇所**であるため、`人間` のまま残す。

**段階を開けるのは明示の構成変更として行う。** これは受け入れ可否の表明の規律が
「恒久的に上位へ残す領域」として名指ししている**ルール自体の変更**にあたる。黙って緩めない。

**段階を下げる方向は、いつでも上位が行える**（開けるより下げる方が安全側であるため、同じ手続きを
要求しない）。**段階の上げ下げはいずれも「規律・知見の変更の裁可」に属する構成変更であり
（上記「主体」節）、`着火` role とは別**——上記「段階を開けるのは明示の構成変更として行う」が
既に `上位` を使っているのと揃える。

## 段階1・2と本体のルールの対応

段階1・2を開ける＝**人が着火を明示して委譲した**、とみなす。本体（`yosage-dev-harness`）のルール
`implement-routing` は実装 dispatch の着火を人が引くものと定め、その例外を、導入先の profile への本体所定の
宣言（`project-profile` ルールの「実装の着火の委譲」）としている。例外の対象と対象外は `implement-routing` が正本で、
ここでは再記述しない。委譲できる範囲は、その例外の範囲が上限である。

- **段階を開ける操作は2つで1組**: 段階の表を開ける構成変更（上記）と、profile への本体の宣言の記載。片方だけでは
  開いたことにならない。表が段階0なら、宣言があってもリーダーは着火しない。宣言が無ければ、表を開けても
  本体の側で人が引く。段階を下げるときは表を戻せば足りるが、本体は profile の宣言だけを見るので、宣言も外す
  （外し忘れても、リーダーの規律としては表が止める）。
- **段階1**（起票済みのうち、自明な小修正の投入着火）: 対象が単発の issue なら、本体の例外の範囲に収まる。
- **段階2**（まとまった単位の投入着火）: 本体の例外の外に出る部分がありうる（まとまった単位の定め方による）。
  **Epic の Sub-issue に当たる着火は、段階2を開けても人が引く**。「まとまった単位」の範囲の取り方は、
  **段階2を開ける判断の時点で決める**（現時点では決めていない）。
- マージは段階に関わらず人が行う（本体の `pr-loop`）。着火の前提（実装入口の OQ ゲート等）も緩まない。

## 段階を開ける判断

段階を開けるのは、上位が明示の構成変更として行う（上記「段階（初期は0）」）。着火を開ける段階1・2は、profile への宣言の記載も要る
（上記「段階1・2と本体のルールの対応」）。判断の材料は、
上位自身が行っている実質的なゲート——マージ前に成果物を実際に見るレビューと、recall → 提案 →
capture のループ——で得ているものを使う。件数・率の基準は置かない。

**反証条件**: 段階を開ける判断が繰り返し話題になり、実質的なゲートだけでは判断できないと上位が
判断した場合——観測の仕組みを、以前の運用記録の仕組み（案件側の記録ファイルへの1件ずつの追記）とは
別の形で設計し直す（以前のものは記録が自己申告に依存し、他の作業に押されて止まった）。

## 通しで進む根拠は「出力ごとの戻しにくさ」で書く

要件化のあと、設計・案の生成・裁定・分解・起票までは通しで進める。**工程ごとに区切らない**——
区切ると**裁定が承認に変わるだけで、人間が挟まる回数は減らない**。

**根拠を「着火しないから安い」と書かない。** 工程で丸めると、通し区間が生む取り消せない出力を
数え落とす。実際に、この区間は次を生む。

| 出力 | 戻しにくさ |
|---|---|
| issue の起票 | 取り下げられるが、**番号と通知は残る**。以後の重複検索にも現れる |
| 知見の追加 | 同上。しかも**将来の前例の原料になる** |
| 接地のための実行 | 調べる手段に「実行してみること」を含むため、**副作用が出うる** |

**これらは受容する。** 受容の理由は、いずれも**内**に閉じており、誤りが残っても**次の判断の材料
として可視のまま残る**（消えるのではなく、誤りとして読める形で残る）ため。**受容していることを
明示する**のが本節の目的であり、「安いから問題ない」と言っているのではない。

**この受容は段階0に固有である。** 着火まで開けた段階では、出力に外向きの不可逆が加わるので、
根拠を立て直す。

## 定常の接点

段階0の進行が、上位の応答を待って止まる点。**主体の判定基準に沿って2つに分ける**——人間で
なければならないものと、位置として上位が持つもの。

**主体の表は5役割を挙げるが、ここに載るのは2つだけである**——残り3役割は、上記「進行が上位の
応答を待って止まる」という本節の性質に当てはまらない。抜き取り検分は上位発の非同期監査であり、
AI の進行を都度止めるものではない。
規律・知見の変更の裁可は下記「止まる条件」側で扱う（触る対象で判定する例外的な停止であり、
進行を待たせて応答を得る定常の接点ではない）。受け入れ（マージ）は上記「主体」節が述べるとおり、
実行の機構ごと別のスキル（「`yosage-dev-leader-harness:merge-recommendation` スキル」）へ委ねられている。

### 人間の接点

1. **要件化ゲート** — 受け入れ条件つきの要件を出し、**その内容を説明し**、納得を得る。
   （要件の作り方は 「`yosage-dev-leader-harness:requirement-intake` スキル」 が正本。ここでは再記述しない。）

### 上位の接点

1. **着火** — 起票した作業を実際に走らせる判断。

着火は `上位` の役割だが、現に上位に居るのは人間であるため、着火も人間の注意を消費する。

**この2つが定常の接点である。** これに加えて、下記「止まる条件」に当たったときは都度止まる。
**「接点は2つだけ」とは言えない**——止まる条件は例外的な経路ではなく、規律上いつでも起こりうる。

## 止まる条件

次のいずれかに当たったら、**そこで止めて報告する**。自分で先へ進めない。

1. **段階の表に無い操作が要るとき**（上記「列挙外は留保する」）。
2. **対象範囲が「外」に及ぶとき**。
3. **触る対象が次のいずれかのとき** — 規律（リーダーハーネスのスキルの本文、および案件のリポジトリのルールに書いたその規律の適応）・**既存の**知見（改廃／他の文脈への昇格）・
   受け入れゲートの設定。
   **知見の新規追加は止まらない**（ルール `knowledge` が一段落ごとの capture を義務づけており、
   ここで止めると通し進行そのものが成立しない）。**判定は「判断の性質」ではなく「触る対象と
   操作」で行う**——性質で判定させると、実行者がどちらに倒したかが記録に残らない。
4. **要件の受け入れ条件が書けないとき**（「`yosage-dev-leader-harness:requirement-intake` スキル」 が
   blocking として扱うと定めている）。

**止まるときは、どこまで進んだかと、何が判断を要するかを書く。** 「判断を待ちます」だけでは、
受け取った側が状況を再構成するコストを払う。

## 越えたことに後から気づいた場合

**復旧を自分で判断せず、報告して止まる。** これは作業者に課している規律
（「`yosage-dev-leader-harness:dispatch-instruction` スキル」 の作業領域の項）と同じで、**逸脱そのものは
宣言では防げないが、被害は防げる**という理由も同じ。

**越えた事実は、報告に含めて上位へ伝える**（報告して止まる、という上記の規律と同じ経路）。

## この宣言が担保できないこと

- **担保できるのは、正直に申告された越境だけである。** 実行するのも報告するのも同じ主体なので、
  **報告しなかった越境はどこにも現れない**。
- したがって**反証条件に「越えた事実の報告がなかった場合」を置いても、それは観測できない**
  （不在は報告に現れない）。**これは限界であって、反証条件ではない。**
- **承認を経由することが、自動的に歯止めになるわけではない。** 規律・知見の変更は受け入れる側も
  中身をほぼ検分しないという実測があるため（「`yosage-dev-leader-harness:adjudication-capture` スキル」 の
  「上げても質が上がらない判断がある」）、**提案して素通り承認される経路は、実質的に自分で
  自分の制約を緩められる**。宣言はこの経路を塞いでいない。

## 反証条件（何が変われば本ルールを見直すか）

- **止まる条件に当たる回数が、実質的に定常の接点になった場合** — 通しで進む設計が成立して
  いないことになるので、工程の区切りを入れ直す。
- **通しで進めた結果、上記の「受容する出力」の中に、可視のまま残るとは言えないものが出た場合**
  — 受容の理由が崩れる。区間の切り方をやり直す。
- **上記「段階を開ける判断」節が定める反証条件に該当した場合** — 同節に従って見直す
  （内容はここに再掲しない）。
- **列挙外を留保する規則が、実際には運用の停止を頻発させた場合** — 表の粒度が細かすぎる。
  行為ではなく対象範囲の側で括り直す。
