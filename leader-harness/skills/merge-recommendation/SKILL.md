# マージ推奨の表明（リーダー運用・不変条件）

> リーダーハーネス（プラグイン `yosage-dev-leader-harness`）の規律。導入先には写さず、プラグインのスキルとして
> 読み込む。案件ごとの適応は、案件のリポジトリのルール（`.claude/rules/` 等）に書く。一般化する価値のある変更は、
> 利用者に報告を提案する（利用者が明示して指示したときだけ配布元へ起票する。導入先の利用者は、配布元が用意する報告の窓口へ）。

受け入れ（マージ）の実行は**一段上のフラクタル**が行う、が現行の不変条件。リーダーはその手前で
**「推奨するか・保留するか」を理由つきで表明する**（表明するだけで実行はしない＝shadow mode）。
目的は2つ:

- **上位の判断材料**: 受け入れる側が、何をもって検証したか・残っている懸念を一目で読めるようにする。
- **前例**: 食い違ったときの**理由**を（表明と同じ PR コメントに、または裁定 capture として知見に）残し、次から同じ判断ができるようにする（裁定 capture と同じ回路）。

**目的は「上位の判断を当てにいく」ことではない**。それを目的にすると、正しさではなく迎合を学習する。
表明するのは結論ではなく**判断基準**であり、食い違いは基準を直す材料として扱う。

## 表明の作法

- **起点は成果物の状態で決める**: 表明は「マージ可能な状態になり、自分の検証が終わった時点」で出す。
  **自分がどの操作をしたか**（draft を ready にした・PR を新規作成した等）**には紐づけない**。
  着手した時点で既に受け入れ可能だった成果物（引き継いだもの・他者が用意したもの・前のセッションの
  続き）でも、検証が終わった時点で起点が成立する。操作に紐づけると、その操作が発生しない経路
  （＝着手時点で既に受け入れ可能だった経路）で起点そのものが生まれない。
  継承した成果物では**自分が新たに検証した実績を要求しない**——他者の検証結果（既存のレビュー結果・
  テスト結果等）を確認したこと自体が「何をもって検証したか」の中身になる。表明にはその確認内容を書く。
  **再検証を義務づけない**（義務づけると起点が重くなり、別の理由で表明が出なくなる）。
- **事前に確定させる**: 上位が判断を示す**前**に表明を記録する。示された後に理由を書かない（後付けの正当化を防ぐ）。
- **対象を状態に紐づける**: 推奨は「この成果物のこの状態」に対して行う（どのコミット時点かを明示する）。
- **内容**: 推奨/保留の別 ＋ 理由 ＋ **何をもって検証したか**（受け入れ条件との照合結果・レビュー結果・
  テストや静的解析の結果）＋ **残っている懸念**（あれば）。
  検証そのものが空振りしていないかの確かめ方は 「`yosage-dev-leader-harness:dispatch-instruction` スキル」 の「「実行した」と「確かめた」の差」節（同節はリーダー自身の確認にも適用する）。
- **実行しない**: 表明は実行の代替ではない。受け入れの実行は上位が行う。
- **確認を挟まない**: 表明は実行を伴わない記録であり、許可を要さない。「表明を出しますか」と尋ねて
  回答を待たない——尋ねて待つ間に上位の判断が下ることがあり、その場合は表明の機会そのものが失われる。
  **報告と同じ手番にまとめてよい**（完了報告に表明への言及を含めれば、報告の直後に判断が下っても
  事前表明は成立している）。ただし置き場所の不変（下記「書き込み先を統一する」＝PR コメント）は変わらない。
- **書き込み先を統一する**: 表明は**対象 PR のコメント**として投稿する（PR 本文には書かない）。理由は下記。

- **出し直しの判定は「内容が変わったか」の一点で行う（経路を列挙しない）**: 出し直すべきかを
  「何が起きたか」（レビュー指摘への対応・下流からの波及・相乗りコミット・依存の更新・生成物の
  差し替え等）で場合分けしない。**経路を列挙する設計は、列挙していない経路で必ず漏れる**——
  レビュー指摘への対応以外の経路（下流からの波及・相乗りコミット）で出し直しが漏れた事例が実際に
  複数回発生している。判定はただ一つ: **表明した時点の状態と、現在の状態が異なるか。** 異なれば
  理由・経路を問わず出し直す。内容の追加・削除・差し替え、依存の更新、生成物の差し替えを含む
  すべての変更が対象。
- **表明には状態の識別子を必ず含める**（コミットハッシュ等。上記「対象を状態に紐づける」）: 目的は、
  **受け入れる側が、表明が指す状態と現在の状態を突き合わせられるようにすること**——表明があること自体は
  外形からは新旧を見分けられず、識別子と現在の状態が一致して初めて「この表明は現在の状態に対して有効」と
  判断できる。内容の変化を説明するコメントを別途投稿しても、それだけでは出し直しにならない（表明の形式
  ——推奨/保留・理由・検証内容・状態の識別子を伴うもの——を満たして初めて出し直しとして数える）。

### なぜコメントに統一するか

**書き込み先が混在すると、後から読み返したとき、片方だけを見て取りこぼす。**
ある案件で抜けた記録を後から復元した際、本文に書いた回とコメントに書いた回が混在しており、
**コメントだけを見ると半数が取りこぼされた**（取りこぼしたこと自体は、件数が合わないと気づくまで分からない）。

コメント側に寄せる理由は2つ。

- **追記になる**。PR 本文への記載は編集＝上書きであり、いつ書かれたかが残らない。表明は「上位が判断を示す**前**に
  確定させる」ことが要件なので、**書かれた時点が残る形**でなければ要件を満たしたことを後から確認できない。
- **状態ごとに並ぶ**。同じ成果物でも状態が変われば表明を出し直す運用（上記「出し直しの判定は『内容が変わったか』の一点で行う」）と噛み合う。

したがって、**修正が入って状態が変わったら、新しいコメントとして表明を出し直す**（既存のコメントを編集しない）。

- **反証条件**: 上の2つの理由がそれぞれ崩れたら、置き場の判断をやり直す。
  - **PR 本文の編集履歴が機械的に取得できるようになった場合**: 「いつ書かれたか」を本文からも復元できる
    ようになれば、「追記でなければ書かれた時点が残らない」という前提が崩れ、本文へ書く選択肢が復活する。
  - **状態ごとに表明を出し直す運用そのものが変わった場合**（例: 成果物ごとに1回だけ表明する形に変えた場合）:
    「状態ごとに並ぶ」という利点が消えるため、置き場の判断をやり直す必要がある。

## 恒久的に上位へ残す領域（委譲が進んでも変えない）

- 仕様・設計判断を含む変更。
- **不変条件やルール自体を変える変更**（自分の制約を自分で緩められる構造を作らない）。
- 受け入れゲートの設定そのものの変更。
- 上位の外（クライアント・顧客）に見える挙動の変更。
- 戻すのが高い変更（データ移行・公開物）。
- **他の文脈へ伝播する知識**（グローバル昇格候補）。局所の記録と違い、誤りが静かに広く効くため。
