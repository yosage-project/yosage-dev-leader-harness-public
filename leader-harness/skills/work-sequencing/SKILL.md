# 作業の順序づけと投入（リーダー運用・不変条件）

> リーダーハーネス（プラグイン `yosage-dev-leader-harness`）の規律。導入先には写さず、プラグインのスキルとして
> 読み込む。案件ごとの適応は、案件のリポジトリのルール（`.claude/rules/` 等）に書く。一般化する価値のある変更は、
> 利用者に報告を提案する（利用者が明示して指示したときだけ配布元へ起票する。導入先の利用者は、配布元が用意する報告の窓口へ）。

複数の issue を**どの順で・どれを同時に・誰に流すか**を決めるのはリーダーの中核業務。
実装そのものは作業部隊が担い、リーダーは**投入計画（ウェーブ）を立て、監視し、統合する**。
個々の実装 dispatch の作法（レーン判定・base ブランチ・worktree 隔離）は実装フラクタル側の
横断ルールが正本であり、本ルールはその**手前の計画**だけを担う（再記述しない）。

## 1. 束を作る（ウェーブ設計）

issue 群を受け取ったら、いきなり全件を投げず**ウェーブに分ける**。分割の判定軸は3つ。

- **共有リソースの競合**（最優先）: 同じ実行環境を占有し合う作業は**同一ウェーブに入れない**。
  典型は開発用コンテナ群・データベース・ホストポート・エミュレータ。
  「ツールチェーンが独立か」で見分ける（例: バックエンドのテストとモバイルのテストは独立＝並列可、
  コンテナ構成そのものを変える作業同士は占有が衝突＝直列）。
- **ファイルの衝突**: 同じファイル・同じ機能の隣接領域を触る作業は同一ウェーブに入れない
  （統合時のコンフリクトはリーダーが解くコストになる）。
- **依存**: 後続の前提を作る作業（土台の修正・共通処理の追加）は先行ウェーブへ。

各ウェーブは「同時に走らせても互いに壊れない」ことを満たす最大集合にする。
**並列度は目的ではない**——競合を避けた結果として決まる。

## 2. 順序を決める（ウェーブ内・ウェーブ間）

同条件なら次の優先順で前に置く。

1. **足元を壊しているもの**（後続作業の検証環境・開発環境を不安定にしている問題）。
2. **明文化された方針・規約への違反**（放置すると他の実装が違反を模倣する）。
3. **修正が小さく効果が確実なもの**（早く閉じて残りの見通しを良くする）。
4. **設計判断を含むもの**（複数案があり、討議・確認を要するもの。後ろのウェーブへ）。

## 3. 投入前に確認する（ゲート）

- **設計判断が要る issue を、判断を確定させずに投入しない**（作業部隊は会話文脈を持たない）。
  判断が要ると分かった時点で、投入前に確定させるか、当該 issue を後ろのウェーブへ回す。
- **共有リソースの占有枠を明示して渡す**: そのウェーブで環境を占有してよいのは誰かを指示に書き、
  占有した側には**使い終わったら解放する**ことまで課す（次のウェーブが使えなくなるのを防ぐ）。
- **投入指示は self-contained に**: 何を書くかの正本は 「`yosage-dev-leader-harness:dispatch-instruction` スキル」（本ルールでは再記述しない）。

## 4. 走り出したら監視し、揃ったら統合する

- 進捗の監視・ストール判定・停止判断は実装フラクタル側のルール `agent-watchdog` が正本（本ルールは重複させない）。
- **完了は「実装が終わったこと」ではなく「レビューを経て受け入れ可能になったこと」**。
  作業部隊はレビュー前の状態で止め、レビューの差配と受け入れ判断はリーダーが行う。
- 次のウェーブは、前ウェーブの**共有リソースが解放され、統合が済んでから**投入する。

## 5. 計画を残す

ウェーブ構成と順序の**理由**（何と何が競合するので分けたか）を残す。
同種の作業が再来したとき、同じ検討を一からやり直さないため。残し方は案件の記録先に従う
（判断としての価値があるものはナレッジへ、進行管理としての価値は issue へ）。
